# ADR-003: Módulo WASM como pacote interno `@ymir/wasm` com alvo de build Node

## Status

Accepted

## Date

2026-07-03

## Context

Hoje o `core/build-wasm.sh` compila o motor com Emscripten mirando o **browser** e copia
`ymir.js`/`ymir.wasm` para `apps/web/public/wasm/` (não commitado — apenas `.gitkeep`). O cliente
carrega esse WASM via import dinâmico no Web Worker.

Com a física movida para o servidor (ADR-001), o **cliente deixa de rodar física**. Apenas o Node
precisa do WASM — e o executa dentro de um `worker_thread` (ADR-002), que usa o ambiente `node` do
Emscripten (não `web`/`worker`, que são para browsers e Web Workers). O artefato precisa de um lar
com fronteira clara e de um alvo de build compatível com Node.

## Decision

Criar um **pacote interno do monorepo** `@ymir/wasm` em `packages/wasm/`, ao lado de
`packages/types/`.

- É um workspace package **privado** (`"private": true`), referenciado por `apps/api` como
  `"@ymir/wasm": "workspace:*"`. **Não é publicado no npm.**
- O build (Emscripten) passa a mirar `ENVIRONMENT=node` com `MODULARIZE`, produzindo
  `ymir.js`/`ymir.wasm` **dentro do pacote**. Os binários continuam **gerados, não commitados**
  (produzidos pelo `build:wasm` do turbo).
- O pacote expõe um loader fino e a interface `SimulationEngine` que o worker consome, escondendo os
  detalhes do Embind/Emscripten.
- `apps/web/public/wasm/` e o carregamento de WASM no cliente são removidos.

## Alternatives Considered

### Alternative 1: WASM direto em `apps/api/wasm/`

- **Description**: Build copia os binários para dentro de `apps/api`; sem pacote novo.
- **Pros**: Menos peças; um único consumidor.
- **Cons**: Mistura artefato de build com a lógica do servidor; loader e interface do motor ficam
  espalhados no `apps/api`.
- **Why rejected**: A fronteira de pacote isola o binário e seu loader, facilita teste isolado e
  mantém `apps/api` só com lógica de aplicação.

### Alternative 2: Manter em `apps/web/public/wasm` e o Node carregar de lá

- **Description**: Reusar o caminho atual.
- **Pros**: Nenhuma mudança no build.
- **Cons**: Acopla `apps/api` a `apps/web`; coloca artefato de servidor em pasta de assets estáticos
  do front; mantém o alvo de build errado (browser).
- **Why rejected**: Acoplamento invertido e alvo de build incorreto para Node.

## Consequences

### Positive

- Fronteira limpa: binário + loader + interface do motor num só lugar, testável isolado.
- Alvo de build correto para Node (`ENVIRONMENT=node`).
- `apps/web` fica mais leve (sem WASM, sem headers COOP/COEP para SharedArrayBuffer se não forem mais
  necessários).

### Negative

- Um pacote a mais no monorepo para manter.
- Requer ajustar `build-wasm.sh`/CMake e a orquestração do turbo (`build:wasm`).

### Risks

- **CI sem Emscripten**: o build do `@ymir/wasm` exige toolchain Emscripten no pipeline — decisão
  reforçada pela estratégia de testes (ver ADR-005).
- **Compatibilidade Node do Embind**: `emscripten::val::global("JSON")` e afins devem funcionar em
  Node; validar no protótipo do loader.

## Implementation Notes

- Ajustar `core/CMakeLists.wasm.txt` (ou um alvo paralelo) para `-sENVIRONMENT=node -sMODULARIZE=1`.
- O `build:wasm` do turbo passa a produzir dentro de `packages/wasm/`.
- Interface `SimulationEngine` espelha a fachada de `YmirBindings.cpp` (addVesselAt, setRudderAngle,
  setThrusterCommand, step, getState, loadEnvironment, setWaveConditions).
