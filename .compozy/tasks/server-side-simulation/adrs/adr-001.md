# ADR-001: Motor de simulação no servidor via WASM em Node, cliente como terminal remoto

## Status

Accepted

## Date

2026-07-03

## Context

Hoje a física roda **localmente no browser**: `apps/web/src/workers/simulation.worker.ts`
executa um loop de 20 Hz que instancia o motor `YmirSimulation` (C++ compilado para WASM via
Embind, `core/src/wasm/YmirBindings.cpp`), com um fallback cinemático em JavaScript
(`apps/web/src/workers/mock-wasm.ts`) quando o `ymir.wasm` não está compilado.

Esse modelo tem limites: cada aba/usuário roda sua própria simulação isolada, a CPU do cliente
é o teto de desempenho, não há estado autoritativo compartilhável, não há como persistir/retomar
uma run, e mantém-se **dois motores** (WASM real e mock JS) que podem divergir de comportamento.

O objetivo declarado é (1) consolidar um **motor único** como fonte de verdade e (2) estabelecer a
**fundação** para persistência de runs e, mais adiante, múltiplos usuários acessando diferentes
simulações. A simulação deve rodar no servidor; o cliente conecta a ela.

O repositório já previa um servidor (`apps/server`, stub C++) com WebSocket + Protobuf nativos, mas
essa opção representa semanas de "encanamento" (escolha de lib WebSocket C++, toolchain Protobuf,
geração de tipos) sem entregar física nova. Precisamos do caminho de menor esforço que atinja o
objetivo, preservando espaço para evoluir depois.

## Decision

Rodar a simulação no **servidor**, hospedando o **mesmo módulo WASM** (`ymir.js`/Embind) dentro de
um processo **Node.js** (na aplicação `apps/api`, Fastify). O servidor é dono do loop de tick e do
estado autoritativo. O cliente (`apps/web`) torna-se um **terminal remoto**: envia comandos e
recebe *snapshots* de estado em tempo real via **WebSocket**, reusando os DTOs JSON já existentes
em `packages/types` (`SimulationStateDTO`).

Consequências diretas da decisão:

- O cliente **não roda física localmente** — nem WASM nem mock. O Web Worker e o `mock-wasm.ts`
  são removidos.
- A superfície pública do `simulationStore` (play/pause/reset/loadScenario/applyEnvironment) é
  preservada; apenas a implementação interna troca de `postMessage` para envio via WebSocket.
- As simulações **continuam rodando no servidor** independentemente da conexão do cliente; o
  cliente pode reconectar e retomar o snapshot atual.
- **Não** se constrói servidor C++ nativo nem Protobuf nesta decisão.

## Alternatives Considered

### Alternative 1: Servidor C++ nativo com WebSocket + Protobuf (`apps/server`)

- **Description**: Cliente fala WebSocket + Protobuf direto com um processo C++ que linka
  `libs/simulation`, `libs/world` etc. (o desenho já esboçado em `docs/planning/prds/phases/phase-03-server.md`).
- **Pros**: Física nativa sem teto de WASM; múltiplas simulações isoladas por thread; alinhado à
  arquitetura documentada.
- **Cons**: Semanas de trabalho de infraestrutura (escolher lib WebSocket C++, integrar Protobuf no
  build, gerar tipos TS a partir do `.proto`); nenhum ganho de física no curto prazo.
- **Why rejected**: Esforço desproporcional ao objetivo do MVP. O teto de WASM é aceitável para o
  caso naval (poucos corpos, 20 Hz). A camada de rede/protocolo escolhida aqui não impede migrar o
  miolo para C++ nativo depois, se necessário.

### Alternative 2: Manter a física no cliente / modo offline

- **Description**: Continuar rodando WASM no browser, opcionalmente com o servidor como recurso
  adicional atrás de flag.
- **Pros**: Sem dependência de servidor para demos/dev; menor mudança imediata.
- **Cons**: Mantém a divergência WASM-vs-mock; não estabelece estado autoritativo nem a fundação
  para persistência e multi-usuário.
- **Why rejected**: Contraria diretamente os objetivos "motor único" e "fundação para persistência".

## Consequences

### Positive

- Motor único de física (fim da divergência WASM-vs-mock).
- Estado autoritativo no servidor — base para persistência e multi-usuário futuros.
- Carga de simulação sai do cliente; o browser só renderiza.
- Reuso máximo do que já existe: mesmo WASM, mesmos DTOs, mesma stack Node/TS.
- Superfície do `simulationStore` inalterada — impacto contido no cliente.

### Negative

- A simulação passa a exigir o servidor online; sem ele, não há física no cliente.
- Introduz latência de rede entre comando e estado (mitigável com interpolação client-side).
- Desempenho limitado pelo teto do WASM em Node (aceitável para o escopo atual).
- Servidor passa a gerenciar ciclo de vida de simulações vivas (limpeza de sims órfãs).

### Risks

- **Sims órfãs acumulando memória**: mitigar com política de expiração/limpeza (detalhar em
  TechSpec) — no MVP, aceitável dado o baixo número de sims simultâneas.
- **Render "picotado" por causa da taxa de rede**: mitigar com interpolação/extrapolação no cliente
  sobre snapshots a 20 Hz.
- **Divergência de trajetória vs. comportamento antigo**: como é o mesmo WASM, o risco é baixo;
  validar com paridade durante a migração.

## Implementation Notes

- O motor no servidor deve espelhar exatamente a fachada `YmirSimulation` de `YmirBindings.cpp`
  para evitar nova divergência.
- Contrato de rede começa em **JSON** (reusa `packages/types`); migrar para binário/Protobuf só se
  o tamanho do snapshot virar gargalo.
- Identidade de simulação (`sim_id`) é necessária desde o MVP para permitir reconexão.
- Detalhes de biblioteca WebSocket, threading/loop, e limpeza de sessões pertencem ao TechSpec.
