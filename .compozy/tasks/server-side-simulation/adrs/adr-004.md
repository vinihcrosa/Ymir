# ADR-004: Transporte WebSocket + JSON com contrato `ClientMessage`/`ServerMessage`

## Status

Accepted

## Date

2026-07-03

## Context

O cliente precisa enviar comandos e receber estado em tempo real de uma simulação que agora vive no
servidor. Hoje a comunicação é local (main thread ↔ Web Worker via `postMessage`), com o contrato
`WorkerMessageDTO` em `packages/types` (union discriminada por `type`, validada com TypeBox).

O `apps/api` (Fastify 4.29, ESM) não tem suporte a WebSocket ainda. O acesso a dados de projeto
(cenários, embarcações, áreas) continua sendo HTTP REST no mesmo `apps/api`.

## Decision

Usar **WebSocket** como transporte de tempo real e **JSON** como serialização, com dois novos DTOs
em `packages/types`:

- **`ClientMessage`** — union discriminada por `type` para comandos (cliente → servidor):
  `CreateSimulation`, `AttachSimulation`, `Play`, `Pause`, `Reset`, `LoadScenario`,
  `SetActuator` (leme/thruster), `LoadEnvironment`.
- **`ServerMessage`** — union discriminada por `type` para eventos (servidor → cliente):
  `SimulationCreated{sim_id}`, `State{SimulationStateDTO}`, `Status{running|paused|ended}`,
  `VesselConfig`, `Error`.

Os payloads reaproveitam os DTOs existentes (`SimulationStateDTO`, `VesselConfigDTO`). O
`WorkerMessageDTO` e o Web Worker do cliente são **aposentados**.

O WebSocket é servido pelo próprio `apps/api` via `@fastify/websocket` (versão compatível com
Fastify 4). O REST de dados permanece inalterado.

## Alternatives Considered

### Alternative 1: Reusar/estender `WorkerMessageDTO` como contrato de rede

- **Description**: Manter o DTO atual e adicionar campos.
- **Pros**: Menos tipos novos.
- **Cons**: Mistura semântica "mensagem de worker" com "mensagem de rede"; o contrato atual é
  unidirecional (worker → UI).
- **Why rejected**: Nomes e direção não refletem a comunicação de rede bidirecional; separar
  `ClientMessage`/`ServerMessage` torna a validação e a evolução mais claras.

### Alternative 2: Protobuf / serialização binária

- **Description**: Contrato binário (o desenho antigo de `phase-03-server`).
- **Pros**: Payloads menores; contrato forte.
- **Cons**: Toolchain de geração TS/C++, mais peças de build.
- **Why rejected**: JSON reaproveita `packages/types` e TypeBox sem toolchain nova; migrar para
  binário só se o tamanho do snapshot virar gargalo (ver ADR-001).

## Consequences

### Positive

- Contrato bidirecional explícito e validado nos dois sentidos (servidor valida comando; cliente
  conhece o shape do evento).
- Reuso total dos DTOs de estado; zero toolchain nova.
- WebSocket e REST no mesmo `apps/api` — um só serviço.

### Negative

- Payload JSON maior que binário (aceitável no escopo atual).
- Adiciona dependência `@fastify/websocket` e uma rota WebSocket.

### Risks

- **Versão de `@fastify/websocket`**: Fastify 4 requer a linha compatível (v8.x), não a v10 (que
  exige Fastify 5). Fixar a versão correta.
- **Validação em caminho quente**: validar cada `State` a 20 Hz pode custar; validar comandos
  (entrada não confiável) sempre, e considerar validar eventos apenas em dev.

## Implementation Notes

- Uma rota WebSocket (ex.: `GET /ws`) faz upgrade e delega ao roteador de mensagens.
- O roteador do thread principal traduz `ClientMessage` → `postMessage` ao worker (ADR-002) e
  worker → `ServerMessage` ao cliente.
- Envelope mínimo: campo `type` obrigatório; `sim_id` nos comandos após a criação.
