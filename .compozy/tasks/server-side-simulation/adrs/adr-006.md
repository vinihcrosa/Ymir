# ADR-006: Ciclo de vida de simulação — `sim_id`, reconexão via `localStorage`, TTL de órfãs

## Status

Accepted

## Date

2026-07-03

## Context

A simulação deve **continuar rodando no servidor** mesmo quando o cliente cai ou fecha a aba, e o
cliente deve poder **reconectar** e retomar o estado atual (requisito da PRD). No MVP há um usuário e
uma simulação; o rumo futuro é multiusuário com várias simulações. É preciso definir como o cliente
reencontra "sua" simulação e por quanto tempo uma simulação sem cliente permanece viva.

## Decision

**Identidade e reconexão:**
- Ao receber `CreateSimulation`, o servidor gera um **`sim_id`** e responde `SimulationCreated{sim_id}`.
- O cliente guarda o `sim_id` no **`localStorage`**.
- Ao reabrir, o cliente lê o `sim_id` salvo e envia `AttachSimulation{sim_id}`; o servidor responde
  com o snapshot/status atual. Se o `sim_id` não existir mais, o cliente limpa o storage e começa do
  zero.

**Limpeza de órfãs:**
- Quando o **último** cliente de uma simulação desconecta, inicia-se um **TTL** (configurável,
  **default 30 min**).
- Se ninguém reconectar (`AttachSimulation`) dentro do TTL, o servidor **encerra** a simulação e
  libera o `worker_thread`.
- Uma reconexão dentro do TTL cancela o timer.

## Alternatives Considered

### Alternative 1: Servidor lista sims ativas para o cliente escolher

- **Description**: Cliente pede a lista de simulações e escolhe qual anexar.
- **Pros**: Útil com várias sims (multiusuário).
- **Cons**: Exige UI de seleção; excesso para um usuário/uma sim.
- **Why rejected**: Fica para a fase de multiusuário; MVP usa `localStorage` sem UI nova.

### Alternative 2: Simulação nunca encerra sozinha

- **Description**: Só para por comando explícito ou restart do servidor.
- **Pros**: Simples.
- **Cons**: Acumula simulações mortas na memória; vaza `worker_thread`s.
- **Why rejected**: Sem persistência nem limite claro, o servidor degrada com o tempo.

### Alternative 3: Encerrar imediatamente ao desconectar

- **Description**: Sim morre junto com a conexão.
- **Pros**: Sem estado órfão.
- **Cons**: Quebra o requisito de reconexão.
- **Why rejected**: Contraria diretamente a PRD.

## Consequences

### Positive

- Cobre "fecho a aba e volto depois" sem deixar workers rodando para sempre.
- Sem UI nova no MVP; fluxo de reconexão automático.
- Base para multiusuário (o `sim_id` já é a chave de sessão).

### Negative

- O servidor precisa gerenciar timers de TTL por simulação.
- `localStorage` prende a reconexão a um navegador/dispositivo (aceitável no MVP).

### Risks

- **`sim_id` inválido/expirado**: tratar `AttachSimulation` de id inexistente devolvendo erro
  claro; cliente limpa o storage e recomeça.
- **Race entre TTL e reconexão**: cancelar o timer de forma atômica ao anexar; encerrar de forma
  idempotente.
- **Colisão/segurança de `sim_id`**: usar id não adivinhável; auth fica para fase futura (rede
  confiável no MVP).

## Implementation Notes

- O `SimulationManager` mantém, por `sim_id`: o `worker`, o conjunto de conexões e o timer de TTL.
- TTL configurável por env/config (default 30 min).
- `Reset` e `Stop` explícitos encerram imediatamente, independentemente do TTL.
