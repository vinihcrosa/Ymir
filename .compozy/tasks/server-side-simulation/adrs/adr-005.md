# ADR-005: Testes contra o motor real; sem mock de engine; WASM compilado no CI

## Status

Accepted

## Date

2026-07-03

## Context

Hoje o cliente tem dois motores: o WASM real e um fallback cinemático em JavaScript
(`apps/web/src/workers/mock-wasm.ts`). O objetivo é **motor único** (ver PRD e ADR-001). A regra
global do projeto exige cobertura de testes ≥ 80%.

Ao mover a física para o servidor, surge a questão de como testar o `SimulationManager`, o worker e
o protocolo sem depender de um binário WASM compilado — sabendo que o CI pode não ter a toolchain
Emscripten por padrão.

## Decision

Os testes rodam contra o **motor real (WASM)**. **Não** há mock/fake de engine. Dados podem ser
mockados (cenários, configs de embarcação), mas o motor **nunca**.

- O `mock-wasm.ts` é **removido** do repositório (não é reaproveitado como fixture).
- O **CI compila o WASM** (`@ymir/wasm` via Emscripten) antes de rodar os testes que dependem dele.
- Testes de integração exercitam o caminho real: comando → worker → motor WASM → snapshot → cliente.

## Alternatives Considered

### Alternative 1: Interface de motor + fake em Node para unit tests

- **Description**: `SimulationManager` depende de uma interface `SimulationEngine`; testes usam um
  fake cinemático; testes com WASM real ficam atrás de um gate.
- **Pros**: CI passa sem Emscripten; testes rápidos.
- **Cons**: Um fake pode divergir do motor real — exatamente a divergência que o projeto quer matar.
- **Why rejected**: Decisão explícita do produto: testes devem ser reais; sem mock de engine.

### Alternative 2: Reaproveitar o mock antigo como fixture de teste

- **Description**: Mover `mock-wasm.ts` para fixture de teste do servidor.
- **Pros**: Reusa código existente.
- **Cons**: Mantém um segundo motor vivo, com risco de divergência.
- **Why rejected**: Mesmo motivo — contraria "motor único" e "testes reais".

## Consequences

### Positive

- Testes exercitam a física real — sem risco de fake divergente.
- Um único motor no repositório; menos superfície de manutenção.
- CI valida o pipeline de build do WASM continuamente.

### Negative

- CI mais pesado e mais lento (passo de build Emscripten obrigatório).
- Testes que tocam o motor exigem o binário compilado localmente também.

### Risks

- **Toolchain Emscripten no CI**: precisa estar disponível (imagem/container com emsdk) — mitigar com
  passo de setup dedicado e cache do build.
- **Tempo de build**: mitigar com cache de artefatos do turbo/Emscripten.
- **Interface `SimulationEngine`**: ainda existe como fronteira de desacoplamento (ADR-003), mas sua
  **única** implementação é o WASM real — não há implementação de teste.

## Implementation Notes

- A interface `SimulationEngine` (ADR-003) desacopla o worker do carregamento do WASM, mas os testes
  a exercitam através da implementação real.
- O CI ganha um estágio: setup emsdk → `turbo run build:wasm` → testes.
- Remover `apps/web/src/workers/mock-wasm.ts` e `mock-wasm.test.ts` e a lógica de fallback no worker
  (que também é removido).
