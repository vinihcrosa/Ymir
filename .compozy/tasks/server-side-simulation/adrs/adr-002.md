# ADR-002: Uma simulação por `worker_thread` do Node

## Status

Accepted

## Date

2026-07-03

## Context

A simulação passa a rodar no servidor dentro do `apps/api` (Fastify, Node, ESM). Cada `step()` do
motor WASM é trabalho de CPU **síncrono**. O Node executa JavaScript em uma única thread por
processo; rodar um ou mais loops de simulação a 20 Hz no event loop principal do Fastify bloquearia
o atendimento de requisições HTTP e mensagens WebSocket durante cada `step()`.

O objetivo de longo prazo (múltiplos usuários, múltiplas simulações) exige isolamento de CPU entre
simulações e entre a simulação e a camada de rede.

## Decision

Cada simulação roda em seu próprio **`worker_thread`** do Node. O thread principal do Fastify não
executa física — apenas roteia mensagens entre o cliente (WebSocket) e o worker correspondente.

- O `SimulationManager` (thread principal) cria/encerra `worker_thread`s e mantém o mapa
  `sim_id → worker`.
- Cada worker carrega o módulo WASM (`@ymir/wasm`), instancia o motor, roda o loop de tick a 20 Hz e
  publica snapshots via `postMessage` para o thread principal, que reencaminha ao(s) cliente(s) via
  WebSocket.
- Comandos recebidos no thread principal são repassados ao worker via `postMessage`.

## Alternatives Considered

### Alternative 1: In-process no event loop principal (`setInterval` por sim)

- **Description**: `SimulationManager` roda os loops no mesmo thread do Fastify.
- **Pros**: Mais simples, sem comunicação entre threads, sem serialização.
- **Cons**: Cada `step()` bloqueia o event loop; latência de HTTP/WS sobe sob carga; não escala.
- **Why rejected**: Viola o requisito de tempo real (respostas < ~100 ms) assim que a simulação
  fica minimamente pesada; não evolui para multiusuário.

### Alternative 2: Processo/serviço Node separado (revive `apps/server` como Node)

- **Description**: Fastify vira apenas gateway; a simulação vive em outro processo.
- **Pros**: Isolamento máximo (falha de um processo não derruba o outro).
- **Cons**: Mais peças para orquestrar (IPC, descoberta, deploy de dois serviços); excesso para o
  MVP.
- **Why rejected**: Complexidade operacional desproporcional; `worker_threads` já isolam CPU dentro
  de um único processo/deploy.

## Consequences

### Positive

- Física não bloqueia a rede — Fastify continua responsivo.
- Isolamento de CPU por simulação; base natural para multiusuário.
- Um único processo/deploy (`apps/api`) — simples de operar.

### Negative

- Comunicação main↔worker exige serialização de mensagens (snapshots e comandos).
- Cada worker carrega sua própria instância do módulo WASM (custo de memória por sim).
- Ciclo de vida de threads a gerenciar (criação, término, término em queda).

### Risks

- **Overhead de serialização de snapshot** a 20 Hz por sim: mitigar mantendo o payload enxuto
  (mesmo `SimulationStateDTO`); revisitar se virar gargalo.
- **Vazamento de threads** se um worker não for encerrado: o `SimulationManager` é a única via de
  criação/término e aplica a política de TTL (ver ADR-006).

## Implementation Notes

- O worker expõe um protocolo interno de mensagens (comando → ação no motor; tick → snapshot).
- O motor é acessado por trás de uma interface (`SimulationEngine`) para manter o worker desacoplado
  dos detalhes do WASM.
- O limite de simulações simultâneas é configurável (thread principal recusa criar além do limite).
